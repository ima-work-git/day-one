# Unit 1 インフラ基盤 — NFR Requirements

## 対象スコープ
本番製品としての非機能要件を定義する。MVP 実装では一部を簡略化するが、設計目標は本番水準とする。

---

## スケーラビリティ要件

### 同時接続ユーザー数
| フェーズ | 目標 | 対応方針 |
|---|---|---|
| **初期（MVP〜）** | 〜100同時接続 | Lambda オンデマンド・DynamoDB オンデマンド（追加設定不要） |
| **成長期** | 〜10,000同時接続 | Lambda Provisioned Concurrency 追加 |
| **拡大期** | 〜100,000同時接続 | マルチリージョン・DynamoDB グローバルテーブル検討 |

**設計方針**: サーバーレス構成（Lambda + DynamoDB オンデマンド）により、100〜1,000程度は追加設定なしで自動スケールアウト。コストも使った分だけのため、初期は100を想定しつつ1,000来ても問題なく対応できる。

---

## 可用性要件

### 目標稼働率
- **SLA**: 99%（月間約7時間のダウンタイム許容）
- **リージョン**: ap-northeast-1（東京）シングルリージョン
- **マルチAZ**: DynamoDB・S3・Cognito は AWS マネージドサービスのため自動でマルチAZ対応

### 障害対応方針
- Lambda・API Gateway は AWS マネージドのため自動フェイルオーバー
- DynamoDB PITR（35日間）で任意時点への復元が可能
- ElevenLabs API 障害時: クローンボイス生成・TTS をキューに積んでリトライ

---

## パフォーマンス要件

### クローンボイス対話レイテンシ（エンドツーエンド）
- **目標**: 3秒以内（STT + LLM + TTS の合計）
- **理想**: 2秒以内（ストリーミング最適化で達成を目指す）
- **現在の技術選定**: ElevenLabs Flash v2.5（75ms）+ Nova 2 Lite（高速）+ Transcribe Streaming で最速構成を実現済み

### その他パフォーマンス目標
| 指標 | 目標値 |
|---|---|
| REST API レスポンス | 500ms 以内（p95） |
| ページロード（LCP） | 3秒以内 |
| クローンボイス生成 | 30秒以内（非同期・バックグラウンド） |
| WebSocket 接続確立 | 1秒以内 |

---

## セキュリティ要件

### 基本レベル（MVP〜本番）
- **通信**: HTTPS 必須（API Gateway・Amplify で自動適用）
- **ストレージ**: S3 SSE-S3（AES-256）サーバーサイド暗号化
- **認証**: Amazon Cognito（JWT トークン・有効期限管理）
- **アクセス制御**: IAM 最小権限原則（Lambda ロールは必要なサービスのみ）
- **パブリックアクセス**: S3 バケットは全パブリックアクセスブロック

### 将来強化（フェーズ2以降）
- KMS カスタムキーによる暗号化強化
- CloudTrail 監査ログ
- VPC 内 Lambda（プライベートサブネット）
- WAF・Shield（DDoS 対策）
- E2E 暗号化

---

## データ保持・バックアップ要件

### DynamoDB
- **PITR（ポイントインタイムリカバリ）**: 有効（過去35日間の任意時点に復元可能）
  - 毎日バックアップではなく、常時変更ログを記録。「3日前の午後2時15分の状態」など細かい指定が可能
  - 35日を超えた過去への復元は不可
- **将来**: 月次オンデマンドバックアップを追加して35日超のデータも保持

### S3
- **バージョニング**: 有効（誤削除・上書きからの復元）
- **ライフサイクル**: 未完了マルチパートアップロードを7日後に自動削除

---

## 監視・アラート要件

### MVP 期間
- CloudWatch Logs（Lambda・API Gateway のログを手動確認）

### 本番運用
- **CloudWatch Alarm** 設定対象:
  - Lambda エラー率 > 1%（5分間）→ メール通知
  - Lambda タイムアウト率 > 0.5%（5分間）→ メール通知
  - API Gateway 5xx エラー率 > 1%（5分間）→ メール通知
  - DynamoDB スロットリング発生 → メール通知
- **通知先**: 開発チームのメールアドレス

### 将来強化
- AWS X-Ray による分散トレーシング（STT→LLM→TTS のボトルネック特定）
- オンコール対応（PagerDuty 等）

---

## 信頼性要件

### Lambda 設定
| Lambda | メモリ | タイムアウト | 用途 |
|---|---|---|---|
| AI パイプライン | 1024MB | 30秒 | STT + LLM + TTS 処理 |
| REST API | 256MB | 10秒 | CRUD・ビジネスロジック |
| WebSocket | 512MB | 15秒 | リアルタイム対話セッション |
| 通知 | 128MB | 10秒 | SES メール送信 |

### エラーハンドリング
- Lambda: Dead Letter Queue（DLQ）を設定して失敗したイベントを保持
- ElevenLabs API 呼び出し: 指数バックオフでリトライ（最大3回）
- クローンボイス生成失敗: ユーザーに通知メールを送信し、再試行を促す
